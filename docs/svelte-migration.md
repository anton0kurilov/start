# Перенос UI на Svelte

[К оглавлению](README.md).

**Статус: реализован Svelte 5 + Vite, новый UI на TypeScript.**
Ниже сохранены архитектура и журнал переноса. SvelteKit, SSR, сервер,
новое хранение и рекомендательная модель в эту работу не включены.

## Цель и неизменяемые свойства продукта

Перенести существующий UI в компоненты, сохранив визуальный язык,
пользовательские сценарии и отзывчивость. Отдельно исправлять
подтверждённые UX-пробелы, не принимая их за обязательную совместимость.

Контракты:

- чтение не ждёт сетевого запроса при наличии локальных данных;
- scroll не прыгает при приходе новых материалов и обновлении отметок;
- одна публикация имеет общую прочитанность во всех видимых копиях;
- отрицательная оценка и прочитанность — разные действия;
- избранность источника и рекомендации не смешиваются;
- auto-mark не срабатывает на программный скролл;
- редактируемые формы не теряют введённый текст при фоновом обновлении;
- действия с источниками и настройки остаются доступны на mobile;
- локальные сценарии не требуют наличия будущего сервера.

Результаты проверок приведены в журнале ниже. Ограничения вне согласованного
объёма сохранены в [аудите](ui-audit.md).

## Предлагаемые границы компонентов

Это дерево ответственности, не обязательное количество файлов.
Не нужно создавать отдельный компонент для каждого контейнера.

```text
App
├── FeedBoard
│   └── FeedColumn × N
│       ├── ColumnHeader
│       ├── NewItemsNotice
│       ├── ColumnRefreshNotice / EmptyState
│       └── FeedCard × N
│           ├── RelativeTime
│           ├── UsefulnessIndicator
│           └── DismissButton
├── FloatingControls
│   └── RefreshToast
└── SettingsDialog
    ├── SettingsNavigation
    ├── SourcesSection
    │   ├── FolderComposer
    │   └── SettingsFolder × N
    │       ├── FolderEditor
    │       ├── FeedRow / FeedEditor
    │       └── FeedComposer — один активный
    ├── InterfaceSection
    ├── PublicationFilterSection
    └── TransferSection

Общие примитивы:
Button, IconButton, TextField, TextareaField, CheckboxOption
```

Рекомендуемая колонка использует тот же `FeedColumn`, но с другими
данными и оформлением. Для неё не нужен второй независимый рендерер
карточек.

## Контракты основных компонентов

Имена ниже условные; здесь описана смысловая граница.

| Компонент                | Получает                                              | Сообщает наружу / делает                                         |
| ------------------------ | ----------------------------------------------------- | ---------------------------------------------------------------- |
| FeedBoard                | Упорядоченные модели колонок                          | Сохраняет горизонтальную позицию                                 |
| FeedColumn               | Стабильный ключ, заголовок, карточки, ошибки, variant | Toggle-read, scroll-to-top; владеет вертикальным scroll и якорем |
| ColumnHeader             | Заголовок, disabled, allVisibleRead                   | Намерение переключить прочитанность                              |
| FeedCard                 | Публикация, visited, dismissed, favorite, usefulness  | Open, dismiss, impression                                        |
| UsefulnessIndicator      | Готовая модель отображения                            | Только отображает; не обучает модель                             |
| FloatingControls         | Время, refreshing, сообщение                          | Refresh, open-settings, dismiss-toast                            |
| SettingsDialog           | Открытие, выбранный раздел                            | Close, смена раздела; управляет focus и scroll-lock              |
| SettingsFolder           | Folder, expanded, editing, drag-state                 | Toggle, edit, delete, reorder, add-feed                          |
| FeedComposer             | Целевая группа, draft, pending, error                 | Submit/cancel; не сохраняет подписку самостоятельно              |
| PublicationFilterSection | Сохранённые фразы и draft                             | Явный save                                                       |
| TransferSection          | Состояние операций                                    | Import/export; обработка файлов остаётся в application-слое      |

Вместо передачи изменяемого глобального объекта в каждую карточку
предпочтительны небольшие готовые модели отображения. Бизнес-правила
сортировки, фильтрации и полезности не должны дублироваться в компонентах.

## Владение состоянием

### Доменное, долговременное

Папки, подписки, их порядок, избранность, настройки, visited/clicked,
события модели. Сохранение выполняется через единый слой данных.
UI выражает намерение, а не напрямую пишет `localStorage`.

### Загруженные данные

Публикации по источникам, ошибки, последнее обновление, состояние
refresh. Сейчас часть этого живёт в `Map` внутри domain; компонентам
нужен читаемый контракт получения обновлений.

Выбран типизированный контроллер над JS-доменом: команды публикуют
отделённые UI-снимки в read-only Svelte store.
Одной мутации старого объекта недостаточно как архитектурного контракта:
подписчики должны понимать, какие данные обновились.

### Состояние приложения

Открытие настроек, активный раздел, одна редактируемая сущность,
целевая группа новой подписки, pending запросов, глобальная ошибка.
Должно быть понятно, какие части сбрасываются при закрытии диалога,
импорте и reset.

### Локальное UI-состояние

Раскрытые группы, черновики форм, selection/caret, карта scroll
разделов, якоря колонок, скрытые сообщения об ошибках, drag preview.
Не сохранять всё это автоматически как пользовательские настройки.

Особенно разделить:

- сохранённые фразы фильтра и несохранённый textarea-draft;
- прочитанность и факт открытия;
- семантическое состояние материала и состояние его конкретной DOM-копии;
- свежесть данных и ход сетевого запроса.

## Стабильная идентичность и позиция чтения

Использовать ключи папок и подписок при выводе списков.
Идентичность карточки внутри колонки должна сохраняться при вставке
публикаций сверху; индекс массива для этого не подходит.

При этом `itemKey` не гарантированно уникален внутри объединённой
колонки: один материал может прийти из разных подписок. Нужно различать
глобальный ключ прочитанности и ключ экземпляра карточки, например
пару source/feed ID + itemKey, с явной политикой дедупликации.

Сохранение DOM через ключи само по себе не гарантирует сохранение
визуального якоря при вставке выше viewport. Перенести поведение из
[reading.ts](../src/app/reading.ts):
замер перед изменением, восстановление после обновления DOM,
подавление ложного auto-mark.

При горизонтальной вставке рекомендуемой колонки отдельно проверить,
какая обычная колонка остаётся перед пользователем. Сейчас код хранит
сырой `scrollLeft`, а не полноценный горизонтальный якорь.

## Стили

1. На первом этапе оставить токены, reset и общие примитивы глобальными.
2. Сохранить классы и размеры до получения визуально сопоставимого UI.
3. Затем переносить локальные стили в компоненты по одному.
4. Проверять селекторы, которые зависят от родителя, например оформление
   карточки внутри рекомендуемой колонки: scoped CSS меняет границы
   такого взаимодействия. Явный variant-проп у карточки может быть проще.
5. Не заменять существующие размеры стандартными размерами сторонней
   библиотеки по пути миграции.

Safe-area, viewport units и горизонтальный scroll — часть layout-контракта,
а не случайные CSS-детали.

## События и жизненный цикл

Предлагаемые пользовательские намерения:
`refresh`, `openItem`, `dismissItem`, `toggleColumnRead`,
`createFolder`, `updateFolder`, `removeFolder`, `reorderFolders`,
`addFeed`, `updateFeed`, `removeFeed`, `toggleFavorite`,
`savePublicationFilter`, `importState`, `exportState`, `resetState`.

Это имена контрактов, не выбранный синтаксис Svelte API.
При переходе на компонентные обработчики не оставлять параллельно
старую DOM-делегацию, иначе один клик может учитываться дважды.

При уничтожении компонентов очищать:

- IntersectionObserver и dwell-таймеры показов;
- интервалы относительного времени;
- refresh scheduler и глобальные keyboard/window listeners;
- таймеры подавления auto-mark;
- requestAnimationFrame автоскролла drag, preview и pointer capture;
- scroll-lock и управление фокусом диалога.

Относительное время выгоднее обновлять одним общим сигналом времени
раз в минуту, а не отдельным interval на каждую карточку.
Пересчёт/обучение модели не должен быть побочным эффектом рендера.

## Порядок переноса

1. **Зафиксировать baseline.** Скриншоты состояний из матрицы,
   детерминированные тестовые ленты, текущие smoke-тесты.
2. **Подготовить границу данных.** Разделить получение данных,
   пользовательские команды и подписку UI на изменения.
3. **Перенести примитивы и оболочку.** Токены, кнопки, поля,
   FAB, диалог и responsive-навигацию без смены внешнего вида.
4. **Перенести чтение.** Карточку и колонку вместе с прочитанностью,
   скроллом, новыми материалами и обработкой ошибок.
5. **Перенести настройки.** Формы, черновики, inline-edit,
   фильтр, import/export и перестановку с клавиатуры.
6. **Проверить parity.** Выполнить матрицу; исправления из аудита
   оформить как явные изменения поведения.
7. **Убрать старый рендерер.** Когда все сценарии обслуживаются
   новыми компонентами и двойных обработчиков нет.

Это этапы работы, не оценка сроков. Смену хранилища, сервер и ML
лучше вести отдельными изменениями с собственными проверками.

## Скорость и будущая работа при сбоях

Бюджет переноса: медиана семи замеров запуска, обновления и отклика
на одинаковом устройстве и данных не ухудшается более чем на 10%.
Методика и итоговые результаты приведены в этапе 6.

Будущий сервер не должен быть обязательным участником локального
переключения отметки или настроек. Если будут добавлены постоянный кэш
и синхронизация, UI должен различать:

- есть сохранённые данные, идёт обновление;
- показаны сохранённые данные, обновление не удалось;
- локальное изменение сохранено, синхронизация ещё не завершена.

Это будущие состояния, не описание нынешних индикаторов.
Реализация IndexedDB, Service Worker, очереди синхронизации и серверной
модели не входит в текущий перенос.

## Реализация: этап 1 — исходная версия

Ветка: codex/svelte-migration. До изменения UI прошли 101 smoke-тест.
Эталонные RSS и время находятся в tests/fixtures/rss.mjs. Сценарий
measure.mjs снимает семь повторов и экраны на 1440/1100/900/721/720/390/320px.
Исходные медианы production-сборки Parcel в Chromium: запуск 125ms,
refresh 100ms, переключение прочитанности колонки 64ms. Скриншоты и
полные замеры сохраняются в игнорируемом output/playwright/baseline.
Публикации, сохранённые отметки и профиль браузера — тестовые.

### Этап 2 — основа

Добавлены Svelte 5, Vite, TypeScript 6, svelte-check и Sass. Новый вход —
index.html и src/main.ts. Команды разработки сохранены, добавлены check,
preview и test:e2e. Все новые компоненты проходят строгую проверку типов.
Контроллер выдаёт read-only store; существующий формат localStorage и
JSON не изменён. prepareView отделяет обновление модели от чтения селекторов.
Parcel пока сохранён до завершающей очистки.

### Этап 3 — чтение

Добавлены keyed-компоненты колонок и карточек, FAB и общие контролы.
Глобальный itemKey сохраняет общую прочитанность; cardKey отделяет
экземпляры из разных подписок. Геометрия чтения вынесена в reading.ts:
якорь, новые материалы, auto-mark и подавление программной прокрутки.
Горизонтальный якорь теперь привязан к ключу колонки. Селекторы чистые,
показы и относительное время имеют управляемый жизненный цикл.
Строгая проверка Svelte проходит без ошибок и предупреждений; исходные
101 smoke-тест по-прежнему проходят.

### Этап 4 — настройки

Перенесены диалог, все разделы, формы подписок и колонок, избранность,
импорт/экспорт, подтверждения и явное сохранение фильтра с «Сохранено».
Черновики не зависят от снимка лент. Drag использует временный порядок
Svelte, отдельный неинтерактивный preview и отмену, без перестановки
управляемых Svelte DOM-узлов вручную. Фокус после клавиатурной
перестановки восстанавливается после обновления DOM.
Первый браузерный прогон нашёл потерю фокуса при переносе; она исправлена.
После исправления проходят все 10 основных production E2E-сценариев.

### Этап 5 — базовые исправления

Диалог управляет фокусом, Tab и inert-фоном. Header колонки доступен
с клавиатуры. Ошибки JSON и редактирования URL показываются в форме;
первый локальный рендер не ждёт RSS. Dismiss обновляет все копии карточки
и индикатор сразу, без пересборки ленты.
Добавлены AbortSignal и поколения данных: reset/import/dispose отменяют
старые запросы, запоздавшие ответы не перезаписывают новый набор данных.
Показы используют один общий IntersectionObserver с очисткой timers,
вместо отдельного observer на каждую карточку. Тесты контроллера проверяют
read-only store, pending, дедупликацию, ошибки, abort и удаление listeners.

### Этап 6 — переключение и приёмка

Удалены Parcel, старый HTML-вход, императивный рендерер, DOM-делегация,
старые взаимодействия колонок и настроек. Геометрия чтения и drag сохранены
в отдельных модулях. Старые тесты DOM адаптированы к контроллеру, геометрии
и реальным браузерным сценариям. README, AGENTS и карта UI обновлены.
Все этапы находятся в одной ветке, отдельными коммитами.

Итоговые проверки:

| Проверка                 | Результат                                                                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| npm run check            | 0 ошибок, 0 предупреждений                                                                                          |
| npm run test:smoke       | 80 тестов: домен, нормализация, контроллер, геометрия, observer                                                     |
| npm run test:e2e         | 15 сценариев Chromium против Vite production preview                                                                |
| npm run build            | Статический dist; JS около 134 kB / 46 kB gzip, CSS 35 kB / 6,4 kB gzip                                             |
| Чтение и настройки       | Сравнение на ширинах 1440, 1100, 900, 721, 720, 390, 320 px                                                         |
| Дополнительные состояния | High/medium/low, visited/dismissed, избранное, пустой экран, ошибка обновления, pending/ошибка формы desktop/mobile |
| Фокус и lifecycle        | Tab/Escape/inert, возврат фокуса, keyboard reorder; abort, снятие listeners, observer и dwell timers                |

E2E проверяют копии публикаций, открытие и среднюю кнопку, прочитанность,
dismiss, фильтр и черновики при refresh, создание/редактирование/избранность,
импорт/экспорт/сброс с подтверждениями, drag/drop/отмену, rollback при отказе
сохранения, удаление колонки во время проверки RSS, auto-refresh скрытой
вкладки, горизонтальный якорь, вставку сверху и подавление ложного auto-mark.
Offline-сценарий проверяет доступность локального UI до завершения запроса;
сохранение публикаций после перезапуска по-прежнему не обещается.

Для скорости использованы 8 колонок × 40 карточек, одинаковые фикстуры,
фиксированное время и отдельный профиль Chromium. Готовность измеряется
внутри страницы после появления всех 320 карточек и двух animation frames;
refresh — до разблокировки кнопки и следующего кадра, read — через два кадра.
Так исключена переменная задержка опроса Playwright. Изолированно повторены
и исходная Parcel-сборка из a7daa41, и новая сборка одним measure.mjs.
Ранние цифры этапа 1 включали задержку опроса и не используются для бюджета.

| Медиана 7 запусков            | Parcel, мс | Svelte, мс | Изменение |
| ----------------------------- | ---------: | ---------: | --------: |
| Запуск                        |        146 |        145 |     −0,7% |
| Refresh                       |        109 |         47 |    −56,9% |
| Отметка прочитанности колонки |         79 |         31 |    −60,8% |

Бюджет +10% соблюдён. Для сохранения скорости настройки создаются при первом
открытии и затем остаются смонтированными; их код входит в начальный bundle,
поэтому первое открытие не требует сети. Форматтеры Intl переиспользуются,
показы обслуживает один observer, история модели в карточки не копируется.

Артефакты сохраняются в игнорируемом output/playwright:
baseline-ready, svelte-ready и visual-report.json. Сравнение RGB с порогом
24/255: настройки на всех семи ширинах и pending/ошибки форм — 0% отличий;
чтение — 0,172–0,485%, модельные состояния — 0,239%. Остаточные отличия
не меняют геометрию карточек; скриншоты дополнительно просмотрены визуально.
Команды воспроизведения при работающем preview:

```bash
node tests/e2e/measure.mjs svelte-ready
node tests/e2e/states.mjs svelte-ready
node tests/e2e/visual-report.mjs baseline-ready svelte-ready
```

APP_URL указывает на отдельный статический сервер с нужной сборкой.
Это локальные измерения Chromium, не гарантия абсолютных значений на другом
устройстве. Safari/Firefox, реальные iOS/Android, screen reader и safe-area
требуют отдельной ручной приёмки; выполненные проверки их не подменяют.

Production остаётся статическим: публикуется весь dist после приёмки.
Ключ start:rss:v1 и JSON-формат совместимы, миграции данных нет. Откат —
предыдущий статический dist; серверный runtime для этого не нужен.
